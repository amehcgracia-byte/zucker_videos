# #348 — Ingest FFmpeg Linux guard and controlled proxy preset A/B

**Scope:** one isolated branch, no production deployment, with no edits to existing
projects or user media. Reuse the real Stage/Companion pipeline methodology in
Montara #265; stage startup and 360 frame-review latency are separate #358.

## Root cause verified on JM Linux VM

Engine `core/normalization.py:normalize_video_record()` unconditionally launched
`-hwaccel videotoolbox -c:v h264_videotoolbox` for each uncached video, caught
FFmpeg failure, then re-ran with `libx264`. VideoToolbox is a macOS backend;
`ffmpeg -encoders` on the production VM exposes `libx264` but no
`h264_videotoolbox`. Direct on-VM FFmpeg invocation returns "Unknown encoder".

This change skips the guaranteed failure on non-macOS, while retaining the
hardware-first/fallback behavior on macOS. Codec, bitrate, resolution, filter,
source signatures, global cache version, outputs and selected paths are not
changed. Added `elapsed_sec` metrics for probe, normalization and full ingest;
existing music, framing and operator recognition behavior remains unchanged.

## Controlled quality/speed hypothesis

`MONTARA_INGEST_PROXY_PRESET=medium` (default, identical to original FFmpeg
default), `fast`, or `veryfast` provides an **optional allowlisted canary** for
software x264 only. Invalid values fall back to `medium`. This is NOT
activated in MAIN, FER or JM. Do not interpret an installed FFmpeg `h264_nvenc`
encoder as proof that an accessible GPU exists.

A synthetic 5-second `testsrc2` file at 960×540, FFmpeg 6.1.1 VM Linux,
2 encoder threads, 2500k target bitrate (source generated separately, then
encoded sequentially at nice +10), gave:

| Preset | Encode wall time | File bytes | PSNR vs generated input |
| --- | ---: | ---: | ---: |
| medium | 2.198 s | 1,522,742 | 48.53 dB |
| fast | 1.790 s | 1,529,538 | 48.36 dB |
| veryfast | 0.842 s | 1,519,978 | 46.86 dB |

`fast` reduces proxy-encoding wall time ~18.6% **on this sample only** and
changes PSNR by -0.17 dB; `veryfast` reduces proxy-encoding wall time ~61.7%
but reduces PSNR by ~1.67 dB. Neither is an end-to-end ingest benchmark.
Do not claim a corresponding improvement to the user's 18-minute estimate.
The synthetic files were cleaned up by the benchmark's temporary directory.
